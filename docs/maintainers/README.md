# 维护者手册

这份文档面向 AnyBot 维护者，解释系统功能和代码结构。

## 大致结构

AnyBot 由四层组成：

1. `core`：核心库。
2. `sdk`：插件作者 SDK。它在 `core` 上提供 typed config、插件命名空间、配置写回、私有数据目录、多轮对话和插件友好的路由入口。
3. `app/host`：运行框架层。它读取 `anybot.yaml`，装配适配器、存储、内置插件和外部插件，维护插件工作区和用户配置。
4. `cmd/anybot`：用户入口。它把工作目录、插件安装、构建、检查、运行和开发脚手架串成用户可执行的命令。

依赖方向必须保持：

```text
cmd/anybot -> app/host -> sdk -> core
app/host -> adapters/onebot11
sdk -> core
adapters/onebot11 -> core
core 不依赖 sdk、app/host、cmd
```

`internal/scaffold` 是 CLI 的脚手架实现，不是公共 API。

## 包职责

`cmd/anybot`

- 命令解析、用户输出、调用 Go 工具链。
- `init` 创建最终用户工作目录。
- `run` 直接按 `anybot.yaml` 运行基础框架。
- `build` 生成并构建包含外部插件的运行框架。
- `up` 构建、同步、检查并运行生成框架。
- `plugin *` 管理外部插件和插件配置。
- `dev *` 生成核心库项目和插件脚手架。

`app/host`

- `Config` 与 `LoadConfig` 负责配置加载和默认值。
- `NewApp` 负责从配置创建 `core.App`。
- `InstallPlugins` 负责按注册表和配置安装插件。
- `PluginWorkspace` 系列函数负责外部插件工作区。
- `config_update.go` 负责插件配置增删改、同步默认值、运行期写回。
- `status.go`、`inspect.go`、`check.go` 负责面向用户的插件状态、详情和检查。
- `store.go`、`config_store.go` 负责把框架数据目录和插件配置写回注入 SDK。

`app/plugins/*`

- 首发内置插件：`help`、`echo`、`admin`、`ratelimit`。
- 每个内置插件都应该用 `sdk.Define` 声明 typed config，走和外部插件一致的安装模型。

`sdk`

- 插件公共入口。普通插件不应直接依赖 `app/host`。
- 大量类型是 `core` 的别名，目的是让插件作者只 import `sdk`。
- SDK 新能力应优先表现为 `*sdk.Context` 的窄接口，而不是鼓励插件拿 `ctx.App()` 操作全局。

`core`

- 最底层运行时。保持协议无关和配置无关。
- 不定义插件模型。可复用插件属于 `sdk`，core 项目内部组织代码时用普通 Go 函数。
- 适配器只需实现 `Adapter`，把协议事件标准化成 `core.Event`，并提供 `ActionClient`。
- 核心库可以单独用于高度定制的 Go 程序。

`adapters/onebot11`

- OneBot v11 适配器、传输、事件解析、消息段转换、类型化动作客户端。
- 支持 `reverse_ws`、`websocket`、`http` 三种传输配置。

`core/message` 与 `sdk/message`

- `core/message` 定义协议无关消息链。
- `sdk/message` 是给插件作者使用的别名与构造器。
- OneBot 专属消息段构造器保留在 `adapters/onebot11`。

`examples`

- 展示核心库、适配器和 SDK 的能力。示例应跟随 API 变动及时更新。

## 最终用户工作目录链路

`anybot init` 做这些事：

1. 写入 `anybot.yaml`。
2. 写入 `.env.example`。
3. 写入工作目录 README。
4. 创建 `plugins.d/`。
5. 确保外部插件工作区存在：`anybot.plugins.yaml`、`plugins.gen.go`、`main.go`、`go.mod`。

生成文件约束：

- `plugins.gen.go` 和生成的 `main.go` 都带 `// Code generated by anybot; DO NOT EDIT.`。
- 非 `-force` 时，如果生成文件不是 AnyBot 管理的文件，应拒绝覆盖。
- 外部插件工作区清单必须能生成稳定 Go 代码。

用户日常应编辑：

- `anybot.yaml`
- `plugins.d/*.yaml`

用户不应手动编辑：

- `plugins.gen.go`
- 生成的 `main.go`
- `anybot.plugins.yaml`，除非知道 Go module 和符号含义。

## 运行链路

`anybot run`

1. `host.LoadConfig` 读取 `anybot.yaml` 和 `plugins.d/*.yaml`。
2. `host.NewLogger` 创建日志器。
3. `host.NewApp` 根据配置创建 `core.App`。
4. `host.InstallPlugins` 按配置安装注册表中的插件。
5. `app.Run` 启动生命周期、任务、观察者、适配器和事件调度。

`anybot run` 使用的是基础 `anybot` 二进制，因此它只能加载基础二进制里已经注册的插件。外部插件需要 `anybot build` 或 `anybot up` 生成新的运行框架。

`anybot build`

1. `host.EnsurePluginWorkspace` 确保工作区文件存在。
2. 同步生成框架对 AnyBot 自身的 `go.mod` 依赖。
3. 同步外部插件的 `require` 和 `replace`。
4. `go mod tidy`。
5. `go build -o anybot-bot .`。

`anybot up`

1. 默认先执行 `build`。
2. 运行 `./anybot-bot plugin sync`。
3. 运行 `./anybot-bot plugin check`。
4. 运行 `./anybot-bot`。

`up` 是最终用户使用外部插件时最完整的入口。

## 核心运行时生命周期

`core.App.Run(ctx)` 的顺序：

1. 设置 observer 生命周期 context。
2. 绑定适配器状态，初始状态为 `starting`。
3. 执行 `OnStart` 钩子。
4. 创建 worker 队列，或在 `workers <= 0` 时走同步调度。
5. 执行 `OnReady` 钩子。
6. 启动生命周期托管任务。
7. 调用 `adapter.Start`。
8. 适配器回调事件，运行时投递到路由和观察者。
9. `ctx` 结束或适配器返回后停止任务，执行 `OnShutdown`，状态变为 `stopped`。

重要语义：

- `OnReady` 发生在 `adapter.Start` 之前，不代表动作客户端已经可用。
- 需要主动发消息的任务应使用 `WaitActionReady` 或监听 `OnAdapterState`。
- `TaskCritical` 任务失败会取消运行并把错误返回给 `Run`。
- observer 不参与路由排序，不受 `Stop`、`Pass` 影响。

## 事件调度与路由

适配器产出 `core.Event`：

- `Type`：标准事件类型，例如 `message`、`notice`、`request`、`meta_event`。
- `DetailType`：细分类型，例如 OneBot v11 的 `group`、`private`、`heartbeat`。
- `Text` 与 `Message`：标准文本与消息链。
- `Raw` 和 `Data`：原始协议数据。

调度流程：

1. 如果配置了 `serial`，先按事件键加锁。
2. 创建 `core.Context`。
3. 先投递 observer。
4. 按路由优先级和注册顺序依次匹配。
5. 匹配成功后执行中间件链和 handler。
6. `ErrPass` 让出当前路由。
7. `ErrStop` 或 `c.Stop()` 停止后续路由。
8. 其他错误交给 `OnError`，没有自定义处理器时写日志。

路由排序：

- `Priority` 越大越先执行。
- 同优先级保持注册顺序。

## 配置模型

框架配置是 `app/host.Config`：

- `runtime`：日志、worker、buffer、串行、数据目录、状态存储。
- `adapter`：协议与传输。
- `security`：超级用户。
- `plugin_config_dir`：拆分插件配置目录。
- `plugins`：内联插件配置。

加载逻辑：

- 配置文件必须是 `.yaml`。
- `plugins.d` 里只读取 `.yaml`。
- `.yml` 是错误，不是兼容格式。
- 如果同一个插件同时出现在 `plugins` 和 `plugins.d`，报重复配置。
- `enabled` 省略时视为启用。

typed config：

- SDK 插件通过 `sdk.Define(manifest, defaultConfig, setup)` 声明默认值。
- 框架从 YAML node 解码到 config struct。
- 解码前递归解析 `!env VAR_NAME`。
- 解码后调用 `Validate() error`。
- `plugin sync` 会递归补齐默认值，同时保留用户显式值和显式 `enabled: false`。

## 外部插件工作区

工作区清单：

```yaml
module: anybot.local/bot
plugins:
  - name: weather
    module: github.com/acme/anybot-weather
    version: v0.1.0
    replace: ../anybot-weather
    symbol: Module
```

`PluginModule` 校验：

- `name` 必须非空，不能带路径分隔符，不能是隐藏名、`.`、`..`。
- `module` 必须是合法 Go module path。
- `version` 非空时必须能通过 Go module 版本校验。
- `symbol` 必须是导出的 Go 标识符。
- 名称和 module 不能重复。

生成代码：

- `plugins.gen.go` import 每个外部插件 module。
- `main.go` 创建运行框架，并把外部插件注册到 registry。
- 生成文件用原子写入。

CLI 的 `plugin add` 在执行多文件更新前会快照可能被改动的文件和目录；中途失败会回滚，避免留下半写工作区。

## SDK 设计原则

SDK 是插件作者的主入口，不是 `core` 的简单转发。

普通插件推荐只使用：

- `sdk.Define`
- `*sdk.Context`
- `sdk/message`
- `sdk.Rule`、`sdk.Middleware`
- `sdk.Dialogue`
- `sdk.ConfigHandle`

谨慎使用：

- `ctx.App()`：逃生口，适合框架级插件。
- `ctx.UseGlobal()`：会影响所有插件和路由。
- `OnError`：全局错误处理，不是插件局部错误处理。

新增 SDK 能力时先判断：

- 是否属于插件作者的常见需求。
- 是否能用插件命名空间隔离。
- 是否会泄漏运行框架实现。
- 是否应放在 `core` 作为更底层能力。

## OneBot v11 适配器

传输类型：

- `reverse_ws`：AnyBot 起 WebSocket 服务端。
- `websocket`：AnyBot 主动连接协议端。
- `http`：AnyBot 调用 HTTP API，可选接收 HTTP 事件回调。

适配器职责：

- 解析 OneBot v11 事件。
- 支持 CQ 字符串和数组消息。
- 将 OneBot 字段标准化到 `core.Event`。
- 将 `core/message.Chain` 转成 OneBot wire message。
- 提供 `Client` 类型化动作。
- 报告动作通道状态给 `core.StatefulAdapter`。

OneBot 专属能力不要上提到 `core`。只有协议无关的动作抽象，例如 `Send(ReplyTarget, message.Chain)`，才属于 `core.ActionClient`。

## 内置插件维护规则

内置插件应当像外部插件一样写：

- 使用 `sdk.Define`。
- 暴露 typed config。
- 有稳定 `Manifest.Name`。
- 默认配置保守。
- 不直接读写 `anybot.yaml`。

当前内置插件：

- `help`：命令帮助。
- `echo`：复读。
- `admin`：超级用户命令。
- `ratelimit`：全局限速中间件。

## 脚手架维护规则

`internal/scaffold` 生成两类东西：

- `dev init`：直接核心库项目。
- `dev plugin`：独立插件或项目内插件。

维护脚手架时要同步：

- 生成代码。
- 生成 README。
- 模板测试。
- CLI 帮助。
- 根文档里的示例命令。

注意当前语义：

- `anybot dev plugin <name>` 默认生成独立插件 module。
- 项目内插件必须显式 `-in-project`。
- 独立插件默认 module 是 `example.com/anybot-plugin/<名称>`，交给别人使用前应改成自己的 module。

## 测试策略

常规验证：

```sh
go test ./...
go vet ./...
git diff --check
```

涉及运行时、配置、CLI 或插件工作区时加：

```sh
go test -race -count=1 ./core ./sdk ./app/host ./cmd/anybot ./adapters/onebot11
```

涉及真实插件链路时，至少跑一遍：

```sh
go build -o /tmp/anybot-cli ./cmd/anybot
root=$(mktemp -d)
/tmp/anybot-cli dev plugin buddy -template companion -dir "$root/buddy"
(cd "$root/buddy" && go test ./...)
/tmp/anybot-cli init -dir "$root/bot"
/tmp/anybot-cli plugin add example.com/anybot-plugin/buddy -name buddy -replace "$root/buddy" -dir "$root/bot"
/tmp/anybot-cli plugin enable buddy -dir "$root/bot"
/tmp/anybot-cli build -dir "$root/bot" -o anybot-bot
(cd "$root/bot" && ./anybot-bot plugin sync && ./anybot-bot plugin check && ./anybot-bot plugin inspect buddy)
```

## 设计检查清单

改动前问这几个问题：

- 这个能力属于最终用户、插件作者、框架维护者，还是核心库使用者？
- 能否保持 `core` 不知道配置文件、插件下载和运行框架？
- 插件作者是否能通过 `sdk.Context` 完成，而不是必须拿 `core.App`？
- 最终用户是否能通过 `anybot plugin status/check/inspect` 理解当前状态？
- 失败时是否会留下半写文件？
- 生成文件是否带生成标记，并避免覆盖用户文件？
- 外部插件是否需要生成后二进制才能做最终检查？
- 文档和脚手架是否同步更新？

## 术语

- “核心库”：`core`。
- “插件 SDK”：`sdk`。
- “运行框架”：最终用户通过 `anybot` 使用的框架层，以及生成后的 `anybot-bot`。
- “工作区”：最终用户的机器人目录。
- “外部插件”：通过 Go module 安装到工作区的插件。
- “项目内 SDK 插件”：直接核心库项目里的 `plugins/` 目录插件，仍然使用 `sdk.Module`。

用户可见文档里统一使用“框架”或“运行框架”。内部包名 `app/host` 保留，因为它描述的是实现层职责，不是产品术语。
